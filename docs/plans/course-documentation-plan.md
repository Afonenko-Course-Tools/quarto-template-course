# Документация расширений и локальная проверка шаблона

План репозитория `quarto-template-course`: обычный Quarto-сайт документации, каталог готовых демонстраций, доступ к исходникам, небольшой Taskfile и будущий ручной маршрут публикации. Текущее внедрение заканчивается локальным рендером и проверкой без GitHub Pages.

Общие решения, ограничения и порядок выпуска: [межрепозиторный план](../../../specs/course-change-plan.md). Перед изменением поведения — анализ актуальной архитектуры и необходимый рефакторинг. Поддерживается только актуальный авторский формат без обратной совместимости; публичные функции Quarto переиспользуются. Код, спецификации, README и примеры обновляются согласованно в соответствующем PR.

## Готовые демонстрации и доступ к исходникам

Минимальные демонстрации хранятся рядом с расширением. Языковые среды разделяются по примерам и задачам проверки внутри этих репозиториев. Полноценные курсы имеют отдельные репозитории и не входят в каталог демонстраций как обязательная часть сборки документации.

Версии демонстраций выбираются вручную; их подготовка выполняется отдельной операцией в необходимой среде. Готовые результаты прикладываются к Releases расширений. Перед публикацией документации выбранные результаты вручную получают в локальный каталог сайта. Публикация не запускает предварительную сборку примеров. Исходники остаются в GitHub-папках примеров; ссылки должны указывать на ревизию, соответствующую показанному рендеру.

Локальный `examples/` сайта содержит полученные готовые демонстрации и исключён из Git. Quarto копирует их как `project.resources`, а страницы руководства и каталога рендерит из `.qmd`. Итоговый `_site/` также исключён из основной ветки. Согласован ручной локальный сценарий через Taskfile: явное получение закреплённых демонстраций, `quarto render`, проверка результата и `quarto publish gh-pages --no-render`. При последующей публикации проверенное дерево отправляется без повторного рендера; готовый сайт находится в `gh-pages`, исходники — в `main`. Текущее внедрение заканчивается локальной проверкой шаблона и не запускает публикацию.

Установка расширения и получение готовой демонстрации имеют разные назначения. Штатный `quarto add` устанавливает содержимое `_extensions`; исходники примеров вне этого каталога не устанавливаются. Готовая демонстрация — отдельный результат для просмотра и публикации, с HTML, ресурсами и QRC. Она не входит в устанавливаемое расширение и не требует языковой среды для просмотра. Установка по GitHub-репозиторию не означает гарантию скачивания только файлов расширения; компактный архив расширения при необходимости распространяется отдельно штатными средствами Quarto.

Для ссылки на всю папку подходит штатный HTML `code-links` с подписью «Исходники примера», иконкой GitHub и явным `href`. Для ссылки на текущий `.qmd` подходят `repo-actions: [source]` с `repo-url`, `repo-subdir`, `repo-branch` либо `code-tools.source: repo`. В книге параметры репозитория задаются в разделе `book`, на сайте — в `website`. Ссылка на файл и ссылка на папку имеют разные назначения.

Каждый пример имеет две характеристики: набор расширений и среду сборки. Их следует показывать отдельно. Наличие пакета в bundle, активация фильтра или плагина и обязательность для результата также имеют разные значения.

## Простое получение готовых ресурсов

Зафиксировано архитектурное ограничение: репозиторий документации хранит простые указатели на фиксированные готовые результаты. Получение результата не превращается в самостоятельный менеджер пакетов. Версии меняются вручную; выбранный инструмент скачивает конкретный файл, распаковывает подготовленное дерево и передаёт его штатному механизму ресурсов Quarto.

По результатам проверки документации устоявшихся инструментов полезны два паттерна: Antora задаёт внешний готовый UI-пакет через URL в playbook; Docusaurus и VitePress копируют статический каталог в публикацию с сохранением структуры. Это аналогии для разделения внешнего результата и сборки сайта, а не предложение менять Quarto на другой генератор.

Для кросплатформенного запуска выбран Task с небольшим `Taskfile.yml`. Фиксированные URL release assets и пути размещения задаются штатными переменными Task; команды получения, рендера, preview и публикации описываются штатными задачами. При необходимости используется локальный включаемый Taskfile, а не отдельный YAML-манифест с собственным Python/TypeScript-парсером. Согласованная публикация документации выполняется локально вручную. Задачи проверки могут повторно использоваться в CI.

Task поддерживает Windows, Linux и macOS и имеет встроенный интерпретатор команд, но внешние утилиты должны быть доступны на каждой платформе. Для скачивания рассматриваются `curl` или `gh release download`, для распаковки — общий набор переносимых операций `tar`. Создание, удаление и замена каталогов при необходимости имеют короткие платформенные команды через штатный `platforms`. Unix-утилиты не считаются доступными на Windows по умолчанию; обязательность Bash, WSL или Git Bash не вводится. Рабочие пути задаются через `dir`, аргументы с путями заключаются в кавычки. Перед заявлением поддержки проверяются получение результата из чистого каталога, путь с пробелами и кириллицей, повторная подготовка, ошибка скачивания и команды сайта на каждой ОС.

Подготовка запускается явно и получает готовый рендер, не исполняя Gradle, CMake и другие средства демонстраций. Обычные render/preview документации используют уже полученные файлы. Результат обновляется целым деревом, чтобы исключить оставшиеся файлы прежней версии; ошибка загрузки или неполный состав останавливают подготовку. Переписывание HTML и QRC потребителем не входит в этот маршрут: подготовленный результат должен сохранять ресурсы и согласованные адреса публикации.

### Этап 5 Сайт документации расширений

- [ ] Сделать обычный Quarto website с разделами возможностей, страницами расширений, руководством начала работы и каталогом примеров.
- [ ] Задать `full` по умолчанию для шаблона и демонстраций; публиковать специально подготовленные демонстрационные решения и комментарии для показа инструментов.
- [ ] Для возможности объяснять задачу, модель, YAML и Markdown, результат, ограничения форматов и необходимые зависимости.
- [ ] Показывать небольшие примеры разметки рядом с результатом. Использовать штатное экранирование Markdown, исполняемых блоков и shortcodes.
- [ ] Предоставить ссылку на полный `.qmd` и папку необходимых файлов каждого законченного примера в GitHub.
- [ ] Разрешить живые нативные примеры разметки непосредственно на страницах руководства. При показе конкретного повторно используемого экспортного задания использовать ссылку или его готовый результат; избегать расхождения поддерживаемых исходников. Обычная независимая демонстрация `exr-*` не считается второй экспортной декларацией.
- [ ] Подготовить матрицу «необходим для результата», «входит в bundle», «активируется конфигурацией».
- [ ] Отдельно показывать требования для просмотра, рендера документов, экспорта и исполнения проекта задания.
- [ ] После выпуска инструментов и артефактов перестроить шаблон на актуальных зависимостях и выполнить локальный рендер и проверку без публикации на GitHub Pages.

Проверки результата: каждый опубликованный фрагмент соответствует работающему примеру; показанный исходник можно получить; заявленные команды выполняются в чистом окружении; каталог не выдаёт экспериментальные или непроверенные операции за завершённую интеграцию.

### Этап 7 Передача результатов и GitHub Pages

- [ ] Размещать готовые демонстрации внутри общего сайта. Центральный поиск охватывает документацию и описания демонстраций, не их учебное содержание.
- [ ] Передавать HTML, ресурсы и каталог QRC из одной ревизии и проекции. Ссылки на GitHub-папку и `.qmd` должны указывать на ту же ревизию.
- [ ] Вручную закреплять выбранную версию примера и обновлять готовый результат отдельно от публикации документации. Сведения о ревизии, версиях и сборке хранить рядом с результатом, не расширяя JSON-контракт QRC произвольными полями.
- [ ] Публиковать готовые демонстрации через неизменяемые Releases; подготовить все assets до публикации draft. Разрешить отдельные Releases демонстраций без изменения версии расширения, сохраняя сведения о зависимостях и исходной ревизии.
- [ ] Хранить готовые демонстрации в Releases расширений. Перед публикацией вручную получать выбранные версии в локальный каталог, исключённый из Git; проверять наличие полного состава HTML, ресурсов и QRC до публикации.
- [ ] Описать указатели на результаты в небольшом нативном файле выбранного инструмента сборки; использовать штатные скачивание и распаковку. Не разрабатывать менеджер пакетов или собственный интерпретатор конфигурации.
- [ ] Использовать `Taskfile.yml` со штатными переменными и задачами; проверить внешние команды на Windows, Linux и macOS без обязательного Bash/WSL и без языковых сред демонстраций.
- [ ] Использовать относительные внутренние переходы готовой демонстрации; внешние QRC-импорты при локальном preview могут вести в закреплённую публичную публикацию. Текущий импорт требует абсолютный HTTP(S) `base-url` с завершающим `/`; потребитель не переписывает готовый HTML.
- [ ] Готовить публикацию из текущих успешных результатов в чистом staging; удалённые страницы не переносить из предыдущего выпуска.
- [ ] Оформить ручной локальный маршрут через Taskfile: явное получение закреплённых готовых демонстраций, рендер документации, проверка сайта, затем отдельная команда `quarto publish gh-pages --no-render` для последующей публикации. В текущем внедрении выполнить маршрут только до локальной проверки. Сборка центральной документации использует подготовленные демонстрации, не запускает их автоматическую предварительную сборку и не устанавливает все языковые среды.

Проверки результата: страницы, каталог и GitHub-исходники одной версии; ссылки внутри книги и на слайды; PDF и материалы доступны; локальный preview; недоступный результат сборки даёт понятную ошибку; неудачная сборка не публикует старый результат как новый; удалённые материалы исчезают из QRC и поиска.

Владельцы и выпуск демонстраций: [общий план примеров и артефактов](../../../specs/course-examples-release-plan.md).
